# Этап 3. Определение требований и состава результата

Вход: наблюдения, ответы и актуальные релевантные части правовой базы. Результат: объяснимая матрица применимости и согласованный состав документов/действий. Название сайта или готовый шаблон не определяют набор требований.

## Последовательность

1. Разделить фактические сценарии: посетитель/покупатель/представитель ребёнка, товар/услуга/доступ, заявка/договор/маркетинг, собственный процесс/подрядчик. Один сайт может содержать несколько разных режимов.

   Для каждого существенно отличающегося направления проверить запись [SP-01–SP-09](07-special-features.md). Если она отсутствует или деятельность не установлена, R-24 получает статус «не хватает фактов», а не «не применяется». Перечень известных карточек ниже не ограничивает поиск специальных требований.
2. Найти все карточки текущей правовой базы. Для версии исследования от 17.09.2026 это PD-01–PD-15, COM-01–COM-12, ADS-01–ADS-14, SEC-01–SEC-14 — 55 карточек. Это контрольный список версии, а не навсегда фиксированный объём.
3. Сверить карточки с маршрутами ниже. Прочитать также существенные правила в пояснениях досье, которым не присвоен ID. Добавить их в матрицу как отдельные требования со ссылкой на норму/раздел.

   Для R-25 дополнительно использовать досье по ссылкам, источникам статуса и практике: исходные 55 карточек трёх базовых досье не исчерпывают эту новую ветку. Разделить требования о рекламе, символике, упоминании организации и материалах, не сводить их к одному общему запрету.
4. Для каждой карточки определить применимость по фактам и исключениям. Если условие неясно, открыть нужный вопрос или адресное правовое исследование. Отсутствие обнаруженного баннера/формы не заменяет анализ.
5. Для применимого правила определить, что требуется: текст, информация в интерфейсе, настройка, действие владельца, договор с подрядчиком либо сочетание. Отдельная страница не всегда нужна.
6. Связать требование с местом выполнения, ответственным и способом проверки. Отделить юридическую обязанность от предложенного способа её исполнения.
7. Проверить противоречия, полноту покрытия и известные ограничения источников. Передать владельцу сайта состав комплекта и существенные условия для согласования; не спрашивать разрешение на каждую рутинную запись.

## Формат строки решения

| Поле | Содержание |
|---|---|
| ID требования | Карточка базы и конкретный сценарий, например PD-02 / заявка или PD-02 / рассылка |
| Применимость | Применяется / не применяется с причиной / недостаточно фактов / требуется уточнение права |
| Факты | ID фактов, источник и дата; отсутствующие факты не заполняются догадкой |
| Основание | Акт, статья/пункт, редакция и дата действия, ссылка и тип источника |
| Логика | Почему условие выполнено или нет; какие исключения рассмотрены |
| Обязательный результат | Конкретная обязанность и область её применения |
| Предлагаемое исполнение | Документ/страница/настройка/процедура; рекомендации помечены отдельно |
| Ответственный | Владелец, разработчик, бухгалтер, маркетинг или иной конкретный исполнитель |
| Проверка | Ссылка на будущий сценарий приёмки и требуемое доказательство |
| Зависимости | Вопросы, другие требования и документы; последствия изменения |

Одна карточка может дать несколько строк: основания заявки и рассылки различаются; возврат готового товара и заказной работы рассматривается отдельно. Нельзя принять решение для всей организации по одному примеру формы.

## Как выбирать документы

| Возможный результат | Условие выбора | Что не считать достаточным основанием |
|---|---|---|
| Сведения о владельце/продавце | Соответствующие требования R-01 | Название бренда вместо установленной стороны |
| Политика обработки данных | Решение R-07 по фактической обработке | Само наличие сайта без анализа процессов |
| Обычное или письменное согласие | Решение R-08 по конкретной цели/категории | «Для любой формы всегда нужна одинаковая галочка» |
| Согласие на рекламу | Решение R-15 | Согласие на исполнение заказа или факт прошлой покупки |
| Согласие на распространение/изображение/лицензия | Раздельные решения R-16/R-18 | Одно универсальное разрешение на всё |
| Условия работы с cookie и механизм выбора | Решение R-09 | Любой cookie автоматически требует один и тот же баннер |
| Оферта/договор/условия доступа/лицензии | Решения R-02/R-05 | Отдельный файл «Оферта» якобы нужен каждому сайту |
| Условия исполнения/доставки/отказа/возврата | R-03/R-05/R-22 | Универсальные сроки для товаров, услуг и подписок |
| Условия UGC и порядок жалоб | R-18 при соответствующей функции | Наличие обычной формы обратной связи |
| Специальный образовательный раздел | Подтверждённая применимость R-19 | Одно название «детский центр» |
| Внутренние процедуры/поручения/уведомления | R-07/R-10–R-14 и другие установленные обязанности | Публикация лишних внутренних документов на сайте «для надёжности» |

## Проверки перед завершением

- Все 55 карточек исходной версии и дополнительные R-21–R-23 учтены; при новой версии набор сравнивается заново. Не ограничиваться числом 55 после обновления.
- По каждой цели есть фактическое назначение, основание и срок/критерий хранения; согласие не назначается автоматически.
- По каждой коммерческой ветке установлены стороны, продукт, момент договора, цена, исполнение, отказ/обращения и расчёты.
- У каждого обязательного результата есть исполнитель и проверка. «Документ нужен» без места применения не считается решением.
- По неприменимым требованиям указана причина; неизвестные не спрятаны в этой категории.
- Известные [ограничения источников](../legal-research/06-verification-log.md), включая ПП №657 и требования ФСТЭК, не получили фиктивный статус полного подтверждения.
- Будущая дата запуска сопоставлена с уже принятыми будущими изменениями.
- Противоречия и не исследованные отрасли отмечены; зависимые финальные документы не выдаются как окончательные.
- R-24 закрыт только с записью о проверенных признаках и результатах выявленных веток. Новые специальные правила добавлены в матрицу сверх исходных 55 карточек, если это требуется.
- R-25 закрыт только с учётом наблюдаемых элементов, назначения, актуального статуса и контекста. Вывод о конкретном нарушении требует основания; подозрение или обнаруженный контакт при неустановленном нарушении всё равно попадают в отчёт.

Итог владельцу сайта: компактная таблица «требуется / почему / какой документ или действие / что осталось выяснить». Не перегружать его всей внутренней матрицей, но сохранять её для проверки полноты.
